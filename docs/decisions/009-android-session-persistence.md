# ADR-009 — Android session persistence and startup restoration

**Status: Accepted** (bug fix, 2026-09-12)

Supersedes nothing. Extends `ADR-004` (authentication domain model) and `ADR-006` D8–D9 (the Android
authentication flow and its offline stance).

References: `BR-001`, `BR-013`, `BR-014`, `BR-031`, `BR-042`, `Project.md` §13–§16 and §28,
`dev.md` §7, §10–§11, `qa.md` §8 and §15, `docs/api/authentication.md` §3.1–§3.3.

## Context

The Android client authenticated correctly while running: sign-in stored the session, and an
expired access token was renewed through `POST /auth/refresh`. But the session lived only in memory.
Closing the app — or the OS reclaiming the process — dropped it, and the next launch always showed
sign-in. The signed-in UI state lived in per-screen ViewModel flags (`signedIn`), which die with the
process for the same reason (`docs/tracker/007-android-customers-list.md` recorded both as out of
scope: "session persistence, sign-out and token refresh").

Two facts shaped the fix:

* `BR-014` requires that field work — and, by extension, an authenticated session — survive a
  restart rather than being silently lost.
* A refresh token is a credential whose only copy is on the device (`BR-046`). Persisting it without
  a way to end the session would be a liability (`Project.md` §16), so persistence and sign-out are
  one change, not two.

## Decisions

### D1 — The session is encrypted at rest with the Android Keystore

The session is stored as one AES-256-GCM blob in an app-private preferences file
(`servora.session`): the ciphertext and a random per-write IV. The key is generated by and never
leaves the Android Keystore.

One blob rather than one preference per field, so a write replaces the pair atomically and a
half-written session can never be restored.

Rejected:

* **`androidx.security:security-crypto` / `EncryptedSharedPreferences`** — deprecated, and it wraps
  exactly this Keystore mechanism; adding a dependency for no gain contradicts `dev.md` §4.
* **Plain `SharedPreferences`** — the refresh token would be readable from a device backup or a
  root-level file read. `AuthTokens` already documents that the token "must be kept in encrypted
  storage".
* **No user-authentication requirement on the key** — restoring field work must not require a
  biometric prompt on every launch. The threat model is credential leakage from storage, not an
  unlocked device in someone's hand.

A session that cannot be decrypted (key invalidated, file corrupted) is treated as no session: the
stored data is cleared and the user signs in again, rather than the app failing to start.

### D2 — `SessionStore` is the single owner, and persistence does not run on the main thread

`SessionStore` keeps the in-memory copy that reads use on any thread and writes through to
`SessionStorage`. `restore()`, `store()` and `clear()` are `suspend` and move their disk work to
`Dispatchers.IO` themselves, so no caller has to remember to. Construction, and therefore any
Keystore work, never touches the main thread.

`SessionStorage` is a small synchronous port, so a test can double it without a device.

### D3 — `SessionManager` owns the authentication state, and restoration has an explicit state

`AuthState` is a three-way state — `Checking | SignedOut | SignedIn(permissions)` — exposed by
`SessionManager` as a `StateFlow`. The UI renders a function of that state alone:

* while `Checking`, a full-screen loading state is shown;
* `SignedOut` shows the authentication flow;
* `SignedIn` shows the authenticated area.

`Checking` exists so no sign-in screen can flash before a still-valid session is restored. Sign-in
(`AuthRepository`) and the existing renewal flow (`SessionAuthenticator`) replace the stored session;
the manager turns that into `SignedIn`. The per-screen `signedIn` flags the UI used to branch on are
gone, so a restored session and a fresh sign-in reach the authenticated area by one path.

### D4 — Startup restoration policy

On the first start of a process, `restore()` reads the persisted session once and decides:

| Stored state | Result |
| --- | --- |
| No session | `SignedOut` |
| Access token not yet expired | `SignedIn` — no network call |
| Access token expired, refresh succeeds | The existing `POST /auth/refresh` flow; `SignedIn` |
| Access token expired, refresh refused (`401`/`400`) | Session cleared; `SignedOut` |
| Access token expired, backend unreachable | Session kept; `SignedIn` |

The last row is deliberate. A renewal that never reached the backend proves nothing about the
session, and `BR-013`/`BR-031` require offline field work to continue; the app therefore opens with
the stored session and lets the existing 401-then-renew path retry once connectivity returns. Only a
refusal the backend actually sent clears the session.

**OPEN QUESTION — a nuance, not new behaviour.** An app that opens offline with an expired access
token shows the authenticated chrome even though no backend call can currently succeed. That is the
already-approved offline-first stance, but the exact offline UX for an expired session (for example
whether to surface a "reconnect to continue" affordance) is not defined by a business rule and is
**not** implemented here (`BR-042`).

### D5 — Sign-out clears the device first, then asks the backend to revoke

`signOut()` clears `SessionStore` and moves the state to `SignedOut` before calling
`POST /auth/sign-out`, which is best-effort. Signing out must work offline (`BR-014`); the captured
access token is still used for the revocation attempt, and a failure to reach the backend leaves the
user signed out locally. The server-side session is revoked when the call succeeds.

### D6 — Sign-out also drops session-scoped UI state

The Customers ViewModel is retained across sign-out, so signing out resets it. Without that, a user
who signs in next could see the previous session's rows until the next read — state that belongs to a
session the backend scoped to the previous user (`BR-001`, `BR-007`).

## Consequences

* A restart restores the session: valid access token immediately, expired token after a silent
  refresh, otherwise sign-in. The login screen no longer flashes on launch.
* Persisting a credential is paired with a way to end it: `POST /auth/sign-out` is now called on
  logout, and the stored session is cleared even when that call cannot be made.
* The Settings tab exposes sign-out only. The other settings surfaces the design defines are separate
  features and are not part of this change.
* Device/emulator QA is required for the Keystore path; it cannot run on a JVM. The store and the
  manager are covered by JVM tests over an in-memory storage double.

## Deferred

| Item | Why it is deferred |
| --- | --- |
| A "reconnect to continue" state for an offline launch with an expired access token | Not decided by a business rule (`BR-042`); see D4 |
| Migrating the stored format | A later schema change needs its own versioned migration of the preferences blob |
| Enrolling the key in biometric/device-credential auth | Not decided; not required to restore field work |
| The remaining Settings surfaces (language, theme, notifications) | Separate features with their own rules |
